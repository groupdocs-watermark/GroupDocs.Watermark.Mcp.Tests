# Core-contract tests, metered licensing tests, and a local-build channel

## What changed

- Target bumped to **26.9.0** (`Directory.Build.props`, `integration.yml` default,
  `examples/*.json`).
- **`MCP_SERVER_DLL` local channel.** `McpServerFixture` now launches a locally built server
  DLL when that variable is set, instead of `dnx <published package>`. The fixture exposes
  which channel it used, and failures name it.
- **`CoreContractTests`** - free, no licence needed. One test per shared defect the
  2026-08-16 audit confirmed on all 12 products: `fileName`-only input resolves; a missing
  file returns the promised `Available files:` listing; a missing required parameter is
  named; failures set `isError`; `get_license_status` is registered and reports a real
  engine version rather than the server's own.
- **`MeteredLicensingTests`** (`Category=Metered`) - metered mode engages, consumption is
  readable and never goes backwards, and the keys never appear in tool output.
- **`metered.yml`** - a separate workflow, `workflow_dispatch` + weekly only.
- `integration.yml` now runs with `--filter "Category!=Metered"`.
- `ToolDiscoveryTests` tool count 5 -> 6 for the Core-shipped `get_license_status`.

## Why

The audit's validation round showed this suite could not have caught the defects it was
meant to cover:

- Every call used `file:{filePath:...}`. The `fileName` form - the one the tool
  descriptions recommend, and the one that crashed all 12 products - appeared in no test
  anywhere.
- The unknown-file oracle was `IsError || contains("not found")`. The opaque
  `An error occurred invoking '<tool>'` sets `IsError`, so **the test passed on the exact
  defect being reported**. `CoreContractTests` asserts the promised text instead.
- Licence-dependent tests silently no-opped and were counted as Passed. So the metered
  tests do **not** skip when unconfigured - they fail, and the gating lives in the CI job
  where it is visible.

Separately, the suite could only ever run against a published package, so a release could
not be verified before it shipped. `MCP_SERVER_DLL` closes that gap.

## Metered testing - read before enabling

**Every run of `metered.yml` spends real credit.** Hence: dispatch/schedule only (never push
or PR), weekly rather than nightly, one OS rather than the 3-OS matrix, and a `concurrency`
group so two runs cannot bill at once.

**Use a dedicated CI metered account with a capped balance, not the production key.**

Secrets required at repository or organization level:

| Secret | Notes |
|---|---|
| `GROUPDOCS_METERED_PUBLIC_KEY` | |
| `GROUPDOCS_METERED_PRIVATE_KEY` | Secret. Never echoed; no `set -x` in any step that can see it |

Secrets are not exposed to `pull_request` runs from forks, which is why there is no PR
trigger.

**The consumption test asserts the invariant, not an increase.** Measured 2026-09-01 against
a real key pair: **the info tools do not bill** - a plain `get_document_info` moves the
counter by exactly 0.0 - so asserting an increase off that call would be permanently red.
What is asserted is that consumption never goes backwards.

## Running locally

Against a local build, with no NuGet publish:

```bash
dotnet build ../GroupDocs.Watermark.Mcp/src/GroupDocs.Watermark.Mcp/GroupDocs.Watermark.Mcp.csproj

MCP_SERVER_DLL=<abs path>/GroupDocs.Watermark.Mcp.dll dotnet test --filter "Category!=Metered"
```

Add the two metered variables and switch to `--filter "Category=Metered"` for the metered set.

## Impact

`CoreContractTests` and the `get_license_status` case in `ToolDiscoveryTests` **will fail
against the previously published package** until 26.9.0 is live - the repo's standing
convention, since the suite targets the published artifact. Use `MCP_SERVER_DLL` to verify
before release.

## Verification

Full free suite green against the local 26.9.0 build via `MCP_SERVER_DLL`. Tier-1 metered
(`get_license_status`, no document opened) verified against a real key pair across all
products: every engine accepted the pair and reported its own version.
